# Skills vs Finetune: Deep Analysis

This document provides a thorough analysis of why the current finetune pipeline struggles and how the Skills approach addresses each bottleneck.

---

## Part 1: Current Finetune Pipeline — Quality Bottlenecks

### 1.1 The Lossy Compression Chain

The current pipeline transforms knowledge through 4 lossy steps before it reaches the trained model:

```
Step 1: PDF/Docs → Chunks + Summaries
        Loss: Structural relationships, cross-references, implicit context

Step 2: Chunks → Synthetic Training Examples (via LLM generation)
        Loss: Nuance, edge cases, reasoning behind rules, counterexamples

Step 3: Synthetic Examples → Training Signal (via LLM-as-judge grader)
        Loss: Grader may reward fluent-but-wrong, penalize correct-but-awkward

Step 4: Training Signal → LoRA Weight Updates (on small base model)
        Loss: Model capacity limits what can be absorbed; catastrophic forgetting
```

**Concrete example**: A user uploads a 200-page medical guideline PDF. The pipeline:
1. Extracts ~150 chunks with headings + summaries (loses inter-section references)
2. Generates ~500 synthetic Q&A pairs grounded in chunks (loses the "why" behind guidelines)
3. Grades synthetic responses with LLM-as-judge (can't verify medical accuracy)
4. Trains Qwen3-4B LoRA (4B params, rank 8 = ~33M trainable params for 200 pages of medicine)

The result: a model that can parrot guideline fragments but fails on cases requiring cross-reference, reasoning, or nuance — exactly the cases where a specialist should excel.

### 1.2 Synthetic Data Quality

**Current generation pipeline** (`generate-initial-data.ts`, `generate-record-variants.ts`):

```
Seed record → LLM rephrases user message → Store as new training record
```

What this captures:
- Surface-level question variations ("Explain X" → "What is X?" → "How does X work?")
- Topic vocabulary and terminology
- Response format/style patterns

What this misses:
- Edge cases and exceptions (the hardest parts of a domain)
- Multi-step reasoning chains
- Contradictions and disambiguations
- Real-world messiness (ambiguous questions, incomplete context)
- Expert intuition ("in this specific situation, rule X doesn't apply because...")

**The fundamental limit**: Synthetic data generated by a general LLM reflects what that LLM *already knows* about the domain, not what the user's specific reference docs uniquely contain. If GPT-4 already knows chess openings well, generating synthetic chess data just repackages GPT-4's knowledge — adding no unique value from the user's uploaded chess book.

### 1.3 Small Model + LoRA Capacity

```
Base model:     Qwen3-4B (~4 billion parameters)
LoRA rank:      8
Trainable:      ~33 million parameters (0.8% of total)
```

For context:
- A 200-page technical PDF contains roughly 50,000-100,000 words
- Encoding this into 33M parameters means ~330-660 params per word
- This is sufficient for **style** (how to respond) but insufficient for **knowledge** (what to respond)

LoRA excels at:
- Adjusting tone, format, and style
- Teaching the model new response patterns
- Reinforcing behaviors the base model already partially knows

LoRA struggles with:
- Injecting entirely new factual knowledge
- Teaching complex multi-step reasoning specific to a domain
- Maintaining consistency across related facts

### 1.4 Grader Calibration

Current grader: LLM-as-judge using `gpt-4o-mini` at temperature 0.0.

**Known failure modes**:

| Failure | Example | Impact on Training |
|---------|---------|-------------------|
| Surface quality bias | Fluent wrong answer scores 0.8, correct terse answer scores 0.5 | Model learns to be confidently wrong |
| Self-similarity bias | LLM rates LLM-generated text higher | Inflated scores → model doesn't improve |
| Missing ground truth | Grader can't verify "Section 3.2 says..." claims | Hallucinations go unpunished |
| Binary behavior | Grader clusters around 0.7-0.8 with low variance | Weak training signal, all examples look equal |
| Context blindness | Grader doesn't see the source docs | Can't evaluate domain correctness |

**The evaluation-training gap**: Dry run uses `gpt-4o-mini` as the rollout model. If the evaluation passes with GPT-4o-mini generating responses, this tells us nothing about how the finetuned Qwen3-4B will perform.

### 1.5 No Runtime Knowledge Access

This is the most critical issue. After training:

```
User question → Finetuned model → Answer (from memory only)
                     ↑
                     No access to:
                     - Original PDFs
                     - Knowledge chunks
                     - Topic hierarchy
                     - Reference material
```

The model must answer from whatever it memorized during training. For knowledge-heavy domains, this is fundamentally insufficient. Human domain experts constantly reference materials — they don't memorize entire textbooks.

## Part 2: Skills Approach — How It Addresses Each Bottleneck

### 2.1 No Lossy Compression

```
Knowledge sources → Directly available at inference time
```

The knowledge chunks extracted from PDFs become first-class runtime artifacts. They're indexed, searchable, and retrievable during every inference call. No information is lost through synthetic data generation.

**For the medical guideline example**: All 150 chunks with full content, cross-references preserved in the index, original section hierarchy maintained. When the model needs to answer about drug interactions, it retrieves the relevant chunks directly — no memorization required.

### 2.2 Curated Examples Instead of Bulk Synthetic Data

Instead of generating 500 synthetic examples to train on, generate ~50-100 high-quality, graded examples that serve as few-shot demonstrations:

```
Current:  Generate 500 examples → Train model on all 500 → Hope it generalizes
Skills:   Generate 100 examples → Grade them → Keep top 30 → Use as few-shot context
```

Fewer, higher-quality examples work better as in-context demonstrations than bulk synthetic data works as training data, because:
- Foundation models are excellent few-shot learners
- Bad examples in training data permanently degrade the model
- Bad examples in few-shot context can be removed and replaced

### 2.3 Foundation Model Capacity

Instead of constraining to a 4B model, leverage the full reasoning capacity of foundation models:

| Capability | Qwen3-4B (finetuned) | Claude/GPT-4 (with skill) |
|---|---|---|
| Context window | ~8K tokens | 128K-200K tokens |
| Reasoning depth | Shallow (small model) | Deep (large model) |
| Instruction following | Moderate | Excellent |
| Knowledge breadth | Limited to training data | World knowledge + skill knowledge |
| Tool use | Basic | Advanced |
| Self-correction | Poor | Good (can verify against sources) |

### 2.4 Self-Verification Replaces Weak Grading

The Skills approach enables **runtime self-verification**:

```
1. Model generates answer
2. Model retrieves relevant knowledge chunks
3. Model checks: "Does my answer align with sources?"
4. Model self-corrects if needed
5. Model cites sources in response
```

This is fundamentally more powerful than pre-training grader evaluation because:
- Verification happens with full context (question + answer + sources)
- The model can iteratively refine rather than having a single shot
- Users can see citations and verify themselves

### 2.5 Direct Knowledge Access

```
User question → Retrieve relevant chunks → Foundation model + context → Answer with citations
                     ↑
                     Full access to:
                     - All knowledge chunks
                     - Topic hierarchy (navigation)
                     - Few-shot examples (demonstration)
                     - Reasoning templates (methodology)
                     - Evaluation rubric (self-check)
```

## Part 3: Head-to-Head Comparison

### 3.1 Quality Dimensions

| Dimension | Finetune | Skills | Winner |
|-----------|----------|--------|--------|
| Factual accuracy | Prone to hallucination (no source access) | Can cite and verify against sources | Skills |
| Reasoning depth | Limited by model size | Full foundation model capability | Skills |
| Domain coverage | Depends on training data breadth | Depends on knowledge base breadth | Tie |
| Response consistency | Inconsistent (training variance) | Consistent (deterministic retrieval) | Skills |
| Edge case handling | Poor (rarely in training data) | Better (can retrieve edge case docs) | Skills |
| Response style/tone | Good (LoRA excels here) | Good (system prompt handles this) | Tie |
| Novel question handling | Fails silently | Can say "I don't know" + explain why | Skills |

### 3.2 Operational Dimensions

| Dimension | Finetune | Skills | Winner |
|-----------|----------|--------|--------|
| Time to first deploy | Hours (train) | Minutes (generate skill) | Skills |
| Iteration speed | Slow (retrain per change) | Fast (edit + test) | Skills |
| Knowledge updates | Full retrain required | Add/edit chunks | Skills |
| Per-call inference cost | Low ($0.001-0.01/call) | Higher ($0.01-0.10/call) | Finetune |
| Inference latency | Fast (~100-500ms) | Slower (~500-3000ms) | Finetune |
| Offline capability | Full (self-contained) | None (requires API) | Finetune |
| Scalability (high volume) | Better (cheap per call) | Expensive at scale | Finetune |
| Debugging/explainability | Black box | Traceable (chunks + examples) | Skills |

### 3.3 User Experience Dimensions

| Dimension | Finetune | Skills | Winner |
|-----------|----------|--------|--------|
| "Wow" factor | Moderate (custom model) | High (immediate specialist) | Skills |
| Feedback loop | Slow (regenerate → retrain) | Fast (edit → test) | Skills |
| Transparency | Low (why did model say X?) | High (model cites chunk Y) | Skills |
| Trustworthiness | Low (may hallucinate confidently) | Higher (grounded in sources) | Skills |
| Customizability | Limited (need new training data) | High (edit prompts, add examples) | Skills |

### 3.4 When Finetune Wins

Despite the Skills approach advantages, finetune is still the better choice for:

1. **High-volume production inference** — If a user will make 100K+ calls/day, the per-call cost of a foundation model is prohibitive. A small finetuned model is ~10-100x cheaper per call.

2. **Latency-critical applications** — Sub-100ms responses require small local models. RAG adds retrieval latency.

3. **Style/behavior-only adaptation** — If the task is "respond in this format" or "use this tone" without needing new knowledge, LoRA is perfect and more efficient.

4. **Edge/offline deployment** — No internet connection, must run locally.

5. **Proprietary model creation** — If the user wants to own and distribute a custom model, finetune produces a tangible artifact (weights).

## Part 4: The Hybrid Strategy (Recommended)

The strongest approach combines both:

### Phase 1: Skills (Immediate Value)
- User uploads docs + sets objective → Skill Package generated in minutes
- Foundation model + skill = instant specialist
- User tests, iterates, refines the skill

### Phase 2: Skill-Augmented Finetune (Optional, Higher Quality)
- The skill-augmented foundation model generates training data
- This data is **higher quality** than current synthetic generation because:
  - The generating model has direct access to knowledge sources
  - Few-shot examples guide generation quality
  - Self-verification catches errors before they become training data
- The resulting finetuned model is better because it trained on better data

### Phase 3: Skill + Finetuned Model (Maximum Quality)
- Deploy the finetuned model with the skill package
- The finetuned model has learned patterns from training
- The skill provides runtime knowledge access for verification
- Best of both worlds: fast inference + knowledge grounding

```
                        Quality
                          ▲
                          │

                          │
```

## Part 5: Risk Assessment

### Skills Approach Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Foundation model API outage | High | Cache common responses; fallback to finetuned model if available |
| Cost at scale | Medium | Offer finetune as cost-optimization path for high-volume users |
| Context window overflow | Medium | Smart retrieval (only relevant chunks); chunk prioritization |
| Foundation model behavior changes | Medium | Pin model versions; regression test suite |
| User expects "custom model" | Low | Position as "AI specialist agent" not "model training" |
| Prompt injection via knowledge | Medium | Sanitize knowledge chunks; separate instruction from data |

### Finetune Approach Risks (current, for comparison)

| Risk | Severity | Status |
|------|----------|--------|
| Model produces specialist-level hallucinations | High | **Active — this is the core complaint** |
| Training on synthetic data limits capability | High | **Active — fundamental architecture issue** |
| Slow iteration discourages experimentation | Medium | Active |
| Small model can't absorb domain knowledge | High | **Active — LoRA capacity limit** |
| No knowledge access at inference | High | **Active — no mitigation possible with current approach** |

## Part 6: Market Context

The industry trend strongly supports the Skills approach:

- **OpenAI Custom GPTs**: Essentially a skills approach (system prompt + knowledge files + tools)
- **Claude Projects**: System prompt + project knowledge + tools
- **Microsoft Copilot Studio**: Skills/plugins augmenting foundation models
- **Google Vertex AI Agents**: Grounding in user data at inference time
- **RAG everywhere**: Every enterprise AI deployment uses retrieval augmentation

Finetune still has a role, but the market has largely shifted toward **augmentation over adaptation** for knowledge-heavy use cases.

## Summary

| Question | Answer |
|----------|--------|
| Why does current finetune underperform? | Lossy compression chain + small model capacity + no runtime knowledge |
| Will Skills produce better specialists? | Yes, for knowledge-heavy domains (the primary use case) |
| Should we abandon finetune? | No — keep as optional optimization for cost/latency |
| What's the recommended strategy? | Skills-first with optional finetune as Phase 2 |
| How much existing work is reusable? | ~70% (knowledge extraction, topic hierarchy, coverage, evaluation) |
| What's the biggest risk? | Inference cost at scale (mitigated by optional finetune path) |
